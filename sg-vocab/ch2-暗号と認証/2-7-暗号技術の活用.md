## 本節的位置

2-1〜2-6 講的是原理（共通鍵、公開鍵、ハイブリッド、署名、PKI）。本節是**落地**：實際使用暗号技術的東西——通信協定、規格、軟體。考題常問「這個技術用了什麼原理、達成什麼」，所以讀法是**回推它用了哪幾個原理**，而不是背名字。
① ECC 是什麼 → ② ECC 在 TLS 的位置 → ③ 郵件加密 → ④ XML 的部分署名 → ⑤ 其他同場出現的應用。

## ① 楕円曲線暗号（ECC）：短鑰匙、同強度

**為什麼需要它**：RSA（Rivest–Shamir–Adleman）要維持安全，就得不斷加長鑰匙（1024 → 2048 → 3072 bit），**鑰匙越長越慢、越耗電**，對手機和 IoT（Internet of Things）是實際負擔。這就是 2-1 危殆化（きたいか）的另一面。

**楕円曲線暗号（だえんきょくせんあんごう，ECC（Elliptic Curve Cryptography））** 用**不同的數學難題**，在短鑰匙下取得同等強度。

| | RSA | ECC |
|---|---|---|
| 類別 | 公開鍵暗号方式 | **公開鍵暗号方式（與 RSA 同類）** |
| 安全性根據 | **素因数分解（そいんすうぶんかい）的困難性** | **楕円曲線上的離散対数問題（りさんたいすうもんだい）** |
| 同等強度的鍵長 | 3072 bit | **256 bit** |
| 速度・耗電 | 慢 | **快、省電**（鑰匙短 → 運算量小） |
| 適用場面 | 傳統用途 | **智慧型手機、IoT 裝置**、現代的 TLS |

> ⚠️ **ECC 是公開鍵暗号，不是 hash**（SHA（Secure Hash Algorithm）屬於 2-5，是不同的東西）。
> **ECC 256 bit ≒ RSA 3072 bit。**

## ② ECC 在 TLS 裡的兩個位置，與 Forward Secrecy

**為什麼說「現在的 TLS 就是在用 ECC」**：TLS（Transport Layer Security）連線裡有兩個地方用到公開鍵暗号，ECC 兩邊都有份：

| 用在哪 | 名稱 | 做什麼 |
|---|---|---|
| **鍵交換** | **ECDHE** | 雙方協商出那把**セッション鍵（session key）**（＝2-4 ハイブリッド的第一步） |
| **署名・証明書** | **ECDSA** | **サーバ証明書（server certificate）的簽章演算法**，RSA 的替代品 |

**TLS 1.3 廢除了 RSA 鍵交換**，只保留 Diffie-Hellman 系的臨時鍵交換，實務上幾乎都是 ECDHE。証明書那邊則是 ECDSA 與 RSA 並存。

### エフェメラル（ephemeral）帶來前方秘匿性

ECDHE 最後的 **E＝Ephemeral（短暫的、用完即丟）**，帶來 **Forward Secrecy（前方秘匿性（ぜんぽうひとくせい））**：

> **即使伺服器的秘密鍵日後外洩，攻擊者也無法解開「過去已經錄下來的」通信。**

原因：每次連線用的是**臨時產生、事後丟棄**的鑰匙；**秘密鍵只用來證明身分，不用來加密資料**。

> 自編例：攻擊者今年把你和銀行的 HTTPS 通信全部錄下，明年偷到銀行伺服器的秘密鍵。沒有 Forward Secrecy → 去年的錄音全部解得開；有 → 一筆都解不開，因為當時的臨時鑰匙早就丟了。

**同一個設計思路的第四次出現**：
**ソルト（salt，1-3）→ ワンタイムパスワード（one-time password，1-5）→ セッション鍵（2-4）→ Ephemeral 鍵交換（2-7）**
共同原則：**限制單次洩漏的影響範圍。**

## ③ 郵件加密：S/MIME vs PGP

郵件要同時做到機密性與署名，兩個代表：

| | **S/MIME** | **PGP** |
|---|---|---|
| **性質** | **規格（標準）** | **軟體** |
| **信任模型** | **PKI／認証局（にんしょうきょく，CA（Certificate Authority））** | **Web of Trust（信頼の輪（しんらいのわ））** |
| **公開鍵怎麼來** | **事前向 CA 申請認證** | **當事人之間直接交換** |
| **導入難度** | 需要 CA、手續多 | **不用登錄，容易導入** |
| **適合場景** | **大量使用者、組織** | **少數人之間** |

### 共通點（考題愛拿來混淆）

> **S/MIME（Secure / Multipurpose Internet Mail Extensions）和 PGP（Pretty Good Privacy）都使用「ハイブリッド暗号方式」＋「デジタル署名（digital signature）」**，達成的效果完全一樣——郵件的**機密性・完全性・認証**。
> **差別只在「公開鍵的正当性從哪裡來」——CA 還是朋友。**

所以這兩個**不是加密技術的差異，是信任模型的差異**。正好呼應 2-3 的 PGP vs PKI，以及 2-6 的結論：**密碼學無法無中生有地創造信任，總得選一個起點。S/MIME 選機構，PGP 選人際關係。**

## ④ XML署名・XML暗号化：把署名的粒度降到「片段」

### 為什麼需要它

2-5 的核心性質：**デジタル署名的完全性是「全有全無」的——改一個位元，驗證就失敗。** 這在「一份檔案、一個人簽、送出去就不動」的情境沒問題。

但 XML（eXtensible Markup Language）文件的典型用途是**企業間的電子商取引（でんししょうとりひき）**：一張訂單經過發注方 → 承認者 → 受注方，**每一關都要加上自己的資料、簽自己那一段**。用一般署名的話，**後面的人一動文件，前面所有人的署名就全毀了。**

> **XML署名（XML Signature）的解法：把署名的粒度從「整份」降到「片段」。**

### 與一般デジタル署名的差異（★必考）

| | **一般的デジタル署名（2-5）** | **XML署名** |
|---|---|---|
| 簽章範圍 | **整份文件，全有或全無** | **可以只簽一部分**＝**部分署名（ぶぶんしょめい）** |
| 多人簽章 | 基本上疊加在整份上 | **不同人簽不同部分**＝**多重署名（たじゅうしょめい）** |
| 改一個字 | **整個署名失效** | **只有被改到的那部分失效**，其他署名仍有效 |

> **考點本身就是「可做部分署名、多重署名」。**

**XML暗号化（XML Encryption）** 是同一件事的機密性版本——**部分暗号化（ぶぶんあんごうか）**：例如只把訂單裡的信用卡號欄位加密，其餘維持明文讓中間系統能處理。

**共通思想：XML 是「結構化」的文件，所以安全措施也可以跟著結構走，不必整份一起處理。**

### ⚠️ 錯過的陷阱：拿 Ajax 混進來的選項

錯誤選項的寫法：先描述「利用 XML 與 JavaScript 的**非同期（ひどうき）HTTP 通信**，**動的に書き換え（どうてきにかきかえ）**網頁內容」，最後在尾巴黏上「然後加上署名」。

**前半段是 Ajax（Asynchronous JavaScript And XML）的定義，與署名完全無關。** 出題者拿另一個同樣含「XML」的技術的**正確描述**，硬接上署名，讓你因為看到 XML 就選它。

> **看到「非同期通信」「動的に書き換え」→ 那是 Ajax，直接排除。**

## 前因後果

- **本節是 Ch2 前六節的落地**——原理換成產品名與規格名：

  | 原理（2-1〜2-6） | 在本節變成 |
  |---|---|
  | 公開鍵暗号方式 | **RSA／楕円曲線暗号（ECC）** |
  | ハイブリッド暗号方式（2-4） | **S/MIME、PGP、TLS** 全部都用它 |
  | デジタル署名（2-5） | **ECDSA**、S/MIME 與 PGP 的署名機能、XML署名 |
  | PKI・認証局（2-6） | **S/MIME 的信任來源** |
  | Web of Trust（2-3） | **PGP 的信任來源** |

- **用原理回推功能**：問「S/MIME 能達成以下哪些？」→ 它是ハイブリッド＋署名，所以**機密性・完全性・認証・否認防止全都有**。
- **信任要有根**：S/MIME vs PGP 的差別不在加密，而在信任的起點選誰。
- **ECC 繞開了「加長鑰匙」這條越走越窄的路**，但**ECC 與 RSA 同樣會被量子電腦攻破**（離散対数與素因数分解都是量子演算法的目標）。所以 ECC 是**當前的最佳解，不是終點**——終點在**耐量子計算機暗号（たいりょうしけいさんきあんごう，PQC（Post-Quantum Cryptography））**。
- **限制單次洩漏的影響範圍**：Ephemeral 鍵交換接上ソルト、ワンタイムパスワード、セッション鍵這條線。
