# 2-7 暗号技術の活用

本節講的是**實際使用暗号技術的東西**——通信協定、規格、軟體、程式語言等。

## 縮寫展開

| 縮寫 | 全名 | 說明 |
|---|---|---|
| **ECC** | **Elliptic Curve Cryptography** | 楕円曲線暗号 |
| **ECDHE** | **Elliptic Curve Diffie-Hellman Ephemeral** | 橢圓曲線的臨時鍵交換 |
| **ECDSA** | **Elliptic Curve Digital Signature Algorithm** | 橢圓曲線的署名演算法 |
| **S/MIME** | **Secure / Multipurpose Internet Mail Extensions** | 郵件加密的**規格** |
| **PGP** | **Pretty Good Privacy** | 郵件加密的**軟體** |
| **TLS** | **Transport Layer Security** | — |

## 楕円曲線暗号（だえんきょくせんあんごう，ECC）

**定位**：**公開鍵暗号方式**的一種，**與 RSA 同類**——**不是 hash**（SHA 屬於 2-5，是不同的東西）。

| 特徵 | 說明 |
|---|---|
| **鍵が短くて同等の強度** | **ECC 256 bit ≒ RSA 3072 bit** |
| **速い・省電力** | 鑰匙短 → 運算量小 |
| **適用場面** | **智慧型手機、IoT 裝置**、現代的 TLS |

RSA 的安全性根據是**素因数分解の困難性**；ECC 則是**楕円曲線上の離散対数問題**。

### ECC 在 TLS 裡的兩個位置

| 用在哪 | 名稱 | 做什麼 |
|---|---|---|
| **鍵交換** | **ECDHE** | 雙方協商出那把 **セッション鍵**（＝2-4 ハイブリッド 的第一步） |
| **署名・証明書** | **ECDSA** | **サーバ証明書 的簽章演算法**，RSA 的替代品 |

**為什麼說「現在的 TLS 就是在用這個」**：
**TLS 1.3 廢除了 RSA 鍵交換**，只保留 ECDHE 這類方式 → **只要是 TLS 1.3 的連線，鍵交換一定走橢圓曲線**。証明書那邊則是 ECDSA 與 RSA 並存。

### Ephemeral（エフェメラル＝使い捨て）と Forward Secrecy

ECDHE 最後的 **E＝Ephemeral（短暫的、用完即丟）**，帶來 **Forward Secrecy（前方秘匿性）**：

> **即使伺服器的秘密鍵日後外洩，攻擊者也無法解開「過去已經錄下來的」通信。**

因為每次連線用的是**臨時產生、事後丟棄**的鑰匙；**秘密鍵只用來證明身分，不用來加密資料**。

**這是同一個設計思路的第四次出現**：
**ソルト（1-3）→ ワンタイムパスワード（1-5）→ セッション鍵（2-4）→ Ephemeral 鍵交換（2-7）**
共同原則：**限制單次洩漏的影響範圍。**

## メール暗号化：S/MIME と PGP

| | **S/MIME** | **PGP** |
|---|---|---|
| **性質** | **規格（標準）** | **軟體** |
| **信任模型** | **PKI／認証局（CA）** | **Web of Trust（信頼の輪）** |
| **公開鍵怎麼來** | **事前向 CA 申請認證** | **當事人之間直接交換** |
| **導入難度** | 需要 CA、手續多 | **不用登錄，容易導入** |
| **適合場景** | **大量使用者、組織** | **少數人之間** |

### 共通點（考題愛拿來混淆）

> **S/MIME 和 PGP 都使用「ハイブリッド暗号方式」＋「デジタル署名」**，達成的效果完全一樣——郵件的**機密性・完全性・認証**。
>
> **差別只在「公開鍵的正当性從哪裡來」——CA 還是朋友。**

**所以這兩個不是加密技術的差異，是信任模型的差異。**
正好呼應 2-3 的 PGP vs PKI，以及 2-6 的結論：**密碼學無法無中生有地創造信任，總得選一個起點。S/MIME 選機構，PGP 選人際關係。**

## XML署名・XML暗号化

| 日文用語 | 讀音 | 英文全名 | 中文解釋 | 常考重點／易混淆點 |
|---|---|---|---|---|
| **XML署名** | — | **XML Signature** | 對 XML 文書施加的デジタル署名 | **可做「部分署名」「多重署名」**——這就是考點本身 |
| **XML暗号化** | — | **XML Encryption** | 對 XML 文書施加的加密 | **可做「部分暗号化」**，只加密特定欄位 |
| **部分署名** | ぶぶんしょめい | — | 只對文書的**一部分**簽章 | |
| **多重署名** | たじゅうしょめい | — | **多人各簽各的部分** | |

### 一般のデジタル署名との違い（★必考）

| | **一般的デジタル署名（2-5）** | **XML署名** |
|---|---|---|
| 簽章範圍 | **整份文件，全有或全無** | **可以只簽文件的一部分** |
| 多人簽章 | 基本上疊加在整份上 | **不同人簽不同部分** |
| 改一個字 | **整個署名失效** | **只有被改到的那部分失效**，其他署名仍有效 |

### 為什麼需要它

2-5 的核心性質是：**デジタル署名 的完全性是「全有全無」的——改一個位元，驗證就失敗。**
這在「一份檔案、一個人簽、送出去就不動」的情境沒問題。

但 XML 文書的典型用途是**企業間的電子商取引**：一張訂單經過 発注方 → 承認者 → 受注方，**每一關都要加上自己的資料、簽自己那一段**。
若用一般署名，**後面的人一動文件，前面所有人的署名就全毀了。**

> **XML署名 的解法：把署名的粒度從「整份」降到「片段」。**

**XML暗号化** 是同一件事的機密性版本——**部分暗号化**，只把訂單裡的信用卡號欄位加密，其餘維持明文讓中間系統能處理。

**共通思想：XML 是「結構化」的文件，所以安全措施也可以跟著結構走，不必整份一起處理。**

### ⚠️ 過去問の罠：Ajax と混同させる選択肢

錯誤選項常寫成：

> 「XML と JavaScript が持つ**非同期の HTTP 通信機能**を使い、Web ページの内容を**動的に書き換えた**上で署名を付与する」

**這是 Ajax（Asynchronous JavaScript And XML）的定義，與署名完全無關。**
出題者拿另一個同樣含「XML」的技術的**正確描述**，在尾巴黏上「署名を付与する」。

> **看到「非同期通信」「動的に書き換え」→ 那是 Ajax，直接排除。**

## 前因後果

**本節是 Ch2 前六節的「落地」——把原理換成實際的產品名與規格名。**

| 原理（2-1〜2-6） | 在本節變成 |
|---|---|
| 公開鍵暗号方式 | **RSA／楕円曲線暗号（ECC）** |
| ハイブリッド暗号方式（2-4） | **S/MIME、PGP、TLS** 全部都用它 |
| デジタル署名（2-5） | **ECDSA**、S/MIME 與 PGP 的署名機能 |
| PKI・認証局（2-6） | **S/MIME 的信任來源** |
| Web of Trust（2-3） | **PGP 的信任來源** |

**考題的出法通常是「這個技術用了什麼、達成什麼」**，所以記憶的方式不是背名字，而是**回推它用了哪幾個原理**。
例如問「S/MIME 能達成以下哪些？」→ 因為它是 ハイブリッド＋署名，所以**機密性・完全性・認証・否認防止全都有**。

**ECC 受到期待的理由，本質上是「危殆化」的另一面**（→ 2-1）：
RSA 要維持安全就得不斷加長鑰匙（1024 → 2048 → 3072 bit），而**鑰匙越長越慢、越耗電**——對手機和 IoT 是實際負擔。
ECC 用**不同的數學難題**，在短鑰匙下取得同等強度，等於**繞開了「加長鑰匙」這條越走越窄的路**。

但要注意：**ECC 與 RSA 同樣會被量子電腦攻破**（離散対数 與 素因数分解 都是量子演算法的目標）。
所以 ECC 是**當前的最佳解，不是終點**——終點在 **耐量子計算機暗号（PQC）**。
