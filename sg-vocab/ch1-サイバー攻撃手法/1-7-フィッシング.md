# 1-7 フィッシング詐欺

重要度：★★★

## 主要な手法

| 日文用語 | 讀音 | 英文 | 中文解釋 | 常考重點／易混淆點 |
|---|---|---|---|---|
| フィッシング | — | phishing | 偽裝成知名企業或金融機構寄信，誘導使用者到**假網站**輸入個資、卡號、帳密 | 入口是**使用者自己點了連結** |
| ファーミング | — | pharming | 竄改名稱解析，使**輸入正確網址也會被導到假網站** | 見下方專節 |
| ワンクリック詐欺 | — | one-click fraud | 點一下按鈕就顯示「入會完成」並要求付款。常見於交友、成人網站 | 見下方專節 |
| クリックジャッキング | — | clickjacking | 用**透明的圖層／iframe** 疊在正規網站上，使用者以為點的是 A，實際點到 B | 可能在無意中洩漏個資或註冊了某服務 |
| Web ビーコン | — | web beacon | 嵌在網頁或 HTML 郵件中的 **1×1 像素透明圖片**，用於蒐集存取資訊 | 見下方專節 |
| ドライブバイダウンロード | — | drive-by download | 只是瀏覽被竄改的網站就中招，利用**瀏覽器或 OS 的脆弱性** | 已於 1-2 出現 |
| スミッシング | — | **SM**S + phi**shing** | 用簡訊發送假訊息（「請確認您的帳戶資訊」）誘導點連結 | 同家族還有 **ビッシング（vishing＝voice phishing）**，用電話語音詐騙 |
| SEO ポイズニング | — | SEO poisoning | **操弄搜尋排名，讓惡意網站出現在搜尋結果前段** | **不是「讓 SEO 變差」，方向相反** |
| リファラ | — | referer | 「使用者從哪一頁連過來的」資訊 | Web ビーコン 蒐集的項目之一 |

## ファーミング

フィッシング 要騙你**點假連結**；ファーミング 讓你**輸入正確網址也會到假網站**。

兩種做法：
1. 竄改使用者電腦裡的 **hosts ファイル**（本機的名稱對應表）
2. 攻擊 **DNS サーバ**，塞入假的對應 → **DNS キャッシュポイズニング**

**最高頻考點**：因為網址列顯示的是**真的網址**，所以「**確認 URL 是否正確**」這個對策對 ファーミング **無效**。
有效的是 **サーバ証明書（伺服器憑證）的確認**——假網站拿不出正牌憑證。題目很愛拿這組對照考人。

（名字由來：phishing 是「釣」，一隻一隻上鉤；pharming 是「養殖」，把整片流量導過來。）

## ワンクリック詐欺

畫面顯示「登録が完了しました。会費は◯◯円です」，並秀出你的 **IP 位址、OS、瀏覽器版本**。

**那些資訊任何網站都拿得到，identify 不到你本人**——秀出來只是為了營造「我已掌握你個資」的錯覺，逼你付錢。

**對策：無視、不付款、絕對不主動聯絡對方**（一聯絡就等於親手交出真正的個資）。
相關詞：**ツークリック詐欺**（多加一次確認點擊，偽裝成「你已同意」以規避法律責任）。

## Web ビーコン

圖片本身沒意義，重點是**瀏覽器去抓這張圖的動作**會把資訊送到對方伺服器：

- IP 位址
- User-Agent（OS／瀏覽器版本）
- 存取時間
- Cookie
- **リファラ（referer）**＝前一頁的 URL

**在 HTML 郵件裡的用途是「開封確認」**——寄件者能知道你**有沒有開、何時開、從哪開**。
對垃圾信業者而言，你一開信就等於宣告「**這個地址是活的**」，之後垃圾信只會更多。

**所以郵件軟體預設「画像の自動表示をオフ」**——這是標準考點。

## 対策

**依「誰該做」分開記，題目常拆成兩種問法：**

| 立場 | 對策 |
|---|---|
| **使用者** | 不點郵件／簡訊裡的連結，改用自己的書籤或手動輸入網址 |
| 使用者 | **確認サーバ証明書**（對 ファーミング 唯一有效的確認方式） |
| 使用者 | 對突然跳出的付款請求一律**無視、不聯絡** |
| 使用者 | 郵件不自動顯示圖片 |
| 使用者 | 保持 OS／瀏覽器更新（對抗 ドライブバイダウンロード） |
| **網站營運者** | **X-Frame-Options** 或 **CSP frame-ancestors** → 宣告本站不得被 iframe 嵌入（クリックジャッキング 對策） |
| 網站營運者 | 取得並正確運用伺服器憑證，使用 HTTPS |
| 網站營運者 | DNS 伺服器的 キャッシュポイズニング 對策（**DNSSEC**） |

## 前因後果

**這一節的共同結構：攻擊的是「人的判斷」，不是「系統的漏洞」。**

1-3 到 1-6 攻擊的是機器——密碼、封包、連線資源。這節攻擊的是**使用者相信眼前畫面的那個瞬間**。所以對策的重心從技術移到**識別能力與習慣**，這也是 SG（管理向考試）特別重視這節的理由。

**攻擊者沿著「防線」一層層往外繞，這條演化鏈值得整個記起來：**

| 防線 | 破解它的攻擊 |
|---|---|
| 「不要開可疑郵件」 | → **ドライブバイダウンロード**：正常網站被竄改，你什麼都沒點 |
| 「不要點郵件裡的連結」 | → **SEO ポイズニング**：你自己搜尋、自己判斷、自己點 |
| 「確認網址是不是真的」 | → **ファーミング**：網址是真的，網站是假的 |
| 「只點我看得到的按鈕」 | → **クリックジャッキング**：你看到的不是你點到的 |

**每一層對策被破解後，剩下的錨點只有「憑證」。** 因為憑證是**第三者（認証局）背書**的，攻擊者無法偽造——這正是 Ch2 公開鍵基盤（PKI）要解決的問題。這節其實是在替 Ch2 鋪路：**當「眼睛看到的」全都不可信時，信任要靠什麼建立？**

**Web ビーコン 則示範了「合法技術與攻擊手法的界線很薄」。**
同一個 1×1 像素，用在網站分析是正當的商業行為，用在垃圾信是攻擊前的偵察（→ 1-4 フットプリンティング）。判斷基準同樣回到 1-2 アドウェア 那條線：**有沒有告知與取得同意**。
