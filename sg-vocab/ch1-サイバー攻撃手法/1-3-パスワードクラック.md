## 本節的位置

1-2 是用惡意程式進門，本節是**直接拿鑰匙開門**：只要密碼被猜中或被偷，攻擊者就以本人身分登入，系統無從分辨。
整節是一場攻防演化：攻擊者猜（①）→ 防守方鎖帳號 → 攻擊者翻轉方向躲鎖定（②）→ 乾脆不猜、用別處外洩的密碼（③）→ 偷到資料庫裡的 hash 再離線破（④）。每一步都是為了繞過上一步的對策。對策的兩個收束點——**ソルト** 與 **多要素認証**——分別在 4-3 ⑥ 與 Ch2 正式展開。

---

## ① 用猜的：從有根據到窮舉

三種猜法依「CP 值」排序，攻擊者通常照這個順序跑：

| 攻擊 | 做法 | 對策 |
|---|---|---|
| **類推攻撃** | 用使用者 ID、姓名、生日、地名、學校等個人資訊推測 | 不要用有意義的字串、個人資訊 |
| **辞書攻撃** | 拿常用字典（password、123456、qwerty、admin…）逐一試 | 不要用字典裡的字 |
| **ブルートフォース攻撃**（brute force attack）＝**総当たり攻撃** | 針對**單一帳號**窮舉所有密碼組合 | **增加字元種類**（大小寫＋數字＋符號）＋**增加長度**——長度的效果大於複雜度 |

> 辞書攻撃 **通常在 ブルートフォース 之前先跑一次**，因為 CP 值高：用少少的嘗試命中最多的弱密碼。

ブルートフォース 的天敵是 **ロックアウト（account lockout）**：連續失敗 N 次就鎖住帳號。它單一帳號一直錯，必定撞上門檻——這是它的致命弱點，也是②的起點。

---

## ② 翻轉方向：躲開 ロックアウト

既然鎖定是「同一帳號失敗太多次」，攻擊者把方向轉 90 度：

| | 固定什麼 | 變動什麼 | 躲掉什麼 |
|---|---|---|---|
| ブルートフォース | **帳號** | 密碼 | —（會撞上 ロックアウト） |
| **リバースブルートフォース**（reverse brute force） | **密碼** | 帳號（大量） | **ロックアウト**：每個帳號只失敗一次 |
| **パスワードスプレー**（password spray） | **密碼** | 帳號＋**分散 IP、拉長時間間隔** | ロックアウト＋「短時間大量失敗」的偵測規則 |

> **三者是同一條演化鏈。唯一判別點是方向：誰固定、誰變動。**

**對策**：ロックアウト 對後兩者無效 → 只能靠**異常登入偵測**，看「同一密碼試多帳號」「分散 IP 的失敗模式」這類跨帳號的樣態。

**自編例**：某公司 500 個帳號、鎖定門檻 5 次。攻擊者每小時只對每個帳號試一次 `Welcome2026!`，從不同 IP 送出——沒有任何帳號被鎖，單看一個帳號也完全正常。

## ③ 不用猜：拿別處外洩的帳密來用

| 攻擊 | 做法 | 差別 |
|---|---|---|
| **パスワードリスト攻撃**（password list attack） | 用**其他網站外洩**的帳密組合，登入別的服務 | 原理 |
| **クレデンシャルスタッフィング**（credential stuffing） | 同原理，**用工具大量自動化反覆嘗試** | **規模與自動化程度**，不在原理 |

> **與系統本身的脆弱性無關**——你的系統再安全也擋不住。成因是使用者**密碼重複使用（使い回し，つかいまわし）**。

這是最難防的一類：帳號密碼都是「正確的」，系統沒有理由拒絕。

| 立場 | 對策 |
|---|---|
| 使用者 | **不要在多個服務用同一組密碼** |
| 組織 | 只能靠 **多要素認証（たようそにんしょう，MFA：Multi-Factor Authentication）**——「知道密碼」已不可信，就再加「持有物」或「生體情報」 |

## ④ 偷到 hash 之後：レインボーテーブル

前三種都是對登入畫面「線上」嘗試。如果攻擊者直接偷走資料庫呢？

### 先理解：密碼怎麼存

密碼**不以原文保存**，資料庫裡存的是 **ハッシュ関数（hash function）** 算出的 **ハッシュ値（ハッシュち，hash value）**。三個性質（Ch2 正式展開）：

| 性質 | 說明 |
|---|---|
| **一方向性（いっぽうこうせい）** | 由原文算 hash 很容易，由 hash 反推原文**在計算上不可行** |
| **固定長** | 不管輸入多長，輸出長度固定 |
| **衝突困難性** | 不同輸入算出相同 hash 極難（碰撞＝衝突，collision） |

### レインボーテーブル 在做什麼

既然不能反推，攻擊者就**改用查表**：事先把大量密碼算好 hash，做成「ハッシュ値 → 原始密碼」對照表，拿到外洩的 hash 直接查。

純粹的全表太大，所以實際用「還原函數」把表壓縮，**用計算時間換儲存空間（time-memory tradeoff）**——這才是 rainbow table 的本質。

> **⚠️ 理解修正：不是「從 hash 找出規律」**——hash 沒有規律可找，那正是一方向性的意義。是「**事先算好、直接查**」。它是**繞過**一方向性，而不是破解它。

### 對策（必考）

| 對策 | 原理 |
|---|---|
| **ソルト（salt）** | 每個使用者加一段**不同的隨機值**再 hash → 同樣的密碼算出不同 hash，**預先算好的表整個失效** |
| **ストレッチング（stretching）** | 反覆 hash 幾千～幾萬次 → 拉長單次計算時間，窮舉與建表成本暴增 |

> ソルト 的巧妙之處：它讓「**事先**」這件事失去意義——每個人的鹽不同，表就得為每個人重算一次，攻擊經濟學直接崩潰。（ソルト 與 ペッパー 的差別 → 4-3 ⑥）

## ⑤ 對策總整理與「定期變更」陷阱

| 攻擊 | 對策 |
|---|---|
| 類推攻撃 | 不用有意義的單字、個人資訊 |
| 辞書攻撃 | 不用字典裡的字 |
| ブルートフォース | 增加字元種類＋長度；**ロックアウト** |
| リバース／スプレー | ロックアウト 無效 → **異常登入偵測** |
| パスワードリスト／クレデンシャルスタッフィング | 不重複使用密碼；組織側靠 **MFA** |
| レインボーテーブル | **ソルト＋ストレッチング** |
| **全部** | **多要素認証**——密碼被破了也擋得住，是最強的單一對策 |

> **⚠️ 愛出的陷阱：「定期變更密碼」現在已不被推薦。**
> 強制定期變更會讓使用者改成有規律的弱密碼（Password01 → Password02）。現行建議是「**不定期變更，但外洩時立即變更**」＋「長且唯一」＋MFA。選項寫「讓使用者定期變更密碼（定期的な変更）」要警覺。

---

## 前因後果

- **攻擊方向翻轉，是為了繞過對策，不是為了更有效率**：ブルートフォース → リバース → スプレー，每一步都是在閃上一步的防守（ロックアウト、短時間大量失敗偵測）。題目考的就是你看不看得出「誰固定、誰變動」。
- **パスワードリスト攻撃 的破口不在系統而在使用者**：不利用任何脆弱性，所以近年正解一律往 **多要素認証** 走——接 Ch2 認証。
- **讓前提不成立**：密碼加長只是提高難度；ソルト 讓「預先算好」這個前提失效，屬於另一個層級（→ 1-10 前因後果軸②）。
- **安全性 vs 利便性取捨**：強制定期變更看似更安全，實際上逼出規律弱密碼——規則若不顧使用者負擔，會被人性抵銷。
- **接 1-10 IoT**：Mirai 靠初期密碼就打下幾十萬台——**密碼的問題不在演算法，在人**。4-3 ⑥ 則把 ソルト・ペッパー・ストレッチング 從防守方的角度補完。

## 待補（考後）

- ハッシュ関数 的具體演算法（MD5／SHA-1／SHA-256）與各自的安全狀態 → Ch2 補齊後回填
- 多要素認証 的三要素分類 → Ch2
- パスワードレス認証（FIDO2／パスキー）的現況
- 各攻擊在實際過去問中的出題頻率
